## Контекст

Проект создаётся с нуля как самостоятельный репозиторий. Требования определены в `proposal.md` и четырёх одобренных спецификациях. Сервис состоит из единственной страницы, асинхронного API и PostgreSQL, запускается локально и разворачивается на одном Linux-сервере через Docker Compose.

Модель точки намеренно ограничена полями `id`, `x` и `y`; отдельного поля позиции нет. Поэтому изменение порядка означает изменение первичных ключей всех точек.

## Цели и границы

### Цели

- Сохранить простой устанавливаемый Python-пакет с единственным импортируемым пакетом `piecewise_linear`.
- Обеспечить полностью асинхронный путь от FastAPI до PostgreSQL.
- Гарантировать атомарное сохранение полного порядка точек.
- Немедленно отражать локальные изменения на графике и согласовывать их с backend.
- Использовать одинаковые контейнерные сборки для воспроизводимого локального запуска и production-развёртывания.

### Не входит в цели

- Авторизация, пользователи и разделение наборов точек.
- Совместное редактирование из нескольких вкладок или несколькими пользователями.
- История изменений, отмена операций и восстановление удалённых точек.
- Несколько графиков, страниц или наборов данных.
- Kubernetes и распределённое развёртывание.

## Решения

### 1. Backend и границы модулей

Backend использует Python 3.13, FastAPI, `asyncpg`, Advanced Alchemy и Alembic. Конфигурация асинхронного движка и сессий, базовая модель, репозиторий и сервис строятся средствами Advanced Alchemy. FastAPI получает асинхронную сессию через зависимость на запрос; транзакции завершаются явно в сервисном слое.

Пакет `backend/src/piecewise_linear` делится на:

- `api` — маршруты, схемы запросов и ответов;
- `core` — конфигурация и жизненный цикл приложения;
- `db` — модель, конфигурация подключения, репозиторий и сервис точек;
- `main.py` — фабрика FastAPI-приложения.

В `backend/src` не создаются другие импортируемые пакеты. Приложение устанавливается как пакет, а не запускается через добавление `src` в `PYTHONPATH`.

Прямое создание инфраструктуры SQLAlchemy отклонено: оно дублировало бы выбранный слой Advanced Alchemy. Синхронный драйвер отклонён, поскольку нарушил бы требование полностью асинхронного backend.

### 2. Модель данных и порядок

Таблица `points` содержит только:

- `id` — положительный целочисленный первичный ключ с PostgreSQL identity-последовательностью;
- `x` — `double precision`;
- `y` — `double precision`.

API и схема базы отклоняют `NaN` и бесконечные координаты. Порядок определяется `ORDER BY id`.

Все изменяющие операции сериализуются общей транзакционной блокировкой таблицы. Добавление получает следующий идентификатор, редактирование изменяет координаты выбранной точки, удаление допускает разрывы в последовательности ID.

Переупорядочивание принимает полный список текущих ID, проверяет, что он является точной перестановкой сохранённого набора, и в одной транзакции:

1. блокирует таблицу;
2. временно переводит ID в непересекающийся отрицательный диапазон;
3. назначает ID `1…N` согласно полученному порядку;
4. синхронизирует identity-последовательность со следующим свободным значением;
5. возвращает полный актуальный список.

Двухфазная перенумерация исключает конфликты уникальности первичного ключа. Отдельное поле `position` отклонено, поскольку нарушает согласованную трёхполевую модель. Дробные или разреженные ключи отклонены как усложняющие контракт порядка.

### 3. HTTP API

Публичный API имеет префикс `/api/v1`:

- `GET /points` — получить упорядоченный список;
- `POST /points` — создать точку;
- `PATCH /points/{id}` — изменить координаты;
- `DELETE /points/{id}` — удалить точку;
- `PUT /points/order` — сохранить полный порядок ID и вернуть перенумерованный список;
- `GET /health/live` — проверить процесс без обращения к БД;
- `GET /health/ready` — выполнить простой запрос к PostgreSQL.

Полные пути образуются добавлением префикса, например `/api/v1/points` и `/api/v1/health/ready`. Ошибки валидации возвращают `422`, отсутствующая точка — `404`, конфликт устаревшего состава при переупорядочивании — `409`, недоступная БД для readiness — `503`.

FastAPI публикует актуальные контракты в `/docs` и `/openapi.json`. Авторизация и WebSocket API не добавляются.

### 4. Frontend и согласование состояния

Frontend использует React, TypeScript и Vite. Единственный экран состоит из адаптивной двухколоночной сетки: редактируемый список слева, SVG-график справа. На узком экране блоки располагаются вертикально.

Для доступного drag-and-drop с поддержкой мыши, касания и клавиатуры используется `dnd-kit`. Кнопок перемещения вверх и вниз нет. График строится через Recharts: `ScatterChart` отображает координаты как числовые значения, `Scatter` соединяет точки прямыми отрезками в переданном порядке, а адаптивный контейнер подстраивает график под доступный размер. Библиотека берёт на себя оси, масштабирование, сетку и пограничные случаи отображения.

Координаты редактируются в строке точки. Допустимое значение немедленно меняет локальное состояние и график; сохранение выполняется после завершения ввода — при потере фокуса или нажатии Enter. Добавление использует компактную форму координат. Удаление требует подтверждения.

Изменяющие запросы из одной вкладки выполняются последовательно. Перед запросом сохраняется последнее подтверждённое состояние. При успехе применяется серверный ответ, при ошибке выполняется возврат к подтверждённому состоянию и показывается сообщение. WebSocket не используется: требование реального времени относится к немедленной реакции текущего интерфейса, а не к синхронизации разных клиентов.

### 5. Миграции и жизненный цикл базы

Alembic хранится в `backend/migrations` и использует метаданные модели Advanced Alchemy. Таблицы не создаются автоматически при старте приложения.

В Compose отдельный одноразовый сервис миграции ожидает готовности PostgreSQL и выполняет `alembic upgrade head`. Backend запускается только после успешной миграции. Откат выполняется командой Makefile с явным указанием целевой ревизии; автоматический downgrade при неудачном деплое не выполняется, чтобы не потерять данные.

### 6. Контейнеры и маршрутизация

Локальный `compose.yaml` запускает PostgreSQL, миграцию, backend и Vite frontend. Исходники могут подключаться в контейнеры для разработки, поэтому локальной машине не требуются Python, `uv` или npm при обычной демонстрации.

Production-конфигурация использует многоэтапные сборки:

- backend собирается через `uv`, а итоговый Python 3.13-образ содержит установленное приложение и зависимости без `uv`;
- frontend собирается Node.js, а итоговый образ содержит только Nginx и статические файлы.

Nginx раздаёт одностраничный frontend, проксирует `/api`, `/docs` и `/openapi.json` в FastAPI и применяет fallback на `index.html` только для frontend-маршрутов. PostgreSQL не публикуется наружу. Конфигурация поступает через переменные окружения; секреты не включаются в образы и репозиторий.

### 7. Инструменты и проверки

Зависимости backend фиксируются в `backend/uv.lock`; настройки Ruff, Pyright, pytest и coverage находятся в `backend/pyproject.toml`. Frontend фиксирует npm-зависимости lock-файлом. Корневой Makefile предоставляет справку и команды установки, запуска, статических проверок, тестов, миграций, сборки и развёртывания.

Сначала реализуется и согласовывается основной код. Только после отдельного одобрения создаются unit-, интеграционные и Playwright E2E-тесты, проверки образов и health endpoints. Это сохраняет установленную контрольную точку рабочего процесса.

### 8. Архитектурные решения и документация

После одобрения design его решения переносятся в краткие ADR проекта: frontend-стек, асинхронный слой данных и использование ID как порядка, контейнерное развёртывание. Репозиторий содержит собственные копии необходимых решений и инструкций и не ссылается на `common` во время сборки или выполнения.

## Риски и компромиссы

- **Изменяемый первичный ключ усложняет ссылки и конкурентные изменения** → внешних ключей и многопользовательского режима нет; операции сериализуются, а frontend отправляет мутации последовательно.
- **Сбой в середине перенумерации может повредить порядок** → все фазы выполняются в одной транзакции, которая полностью откатывается при ошибке.
- **Две вкладки могут работать с устаревшими ID** → backend проверяет полный состав при reorder и возвращает `409`; полноценное версионирование отложено как выходящее за текущую трёхполевую модель.
- **Оптимистичный интерфейс может кратковременно показать несохранённые данные** → хранится подтверждённый снимок, к которому интерфейс возвращается при ошибке.
- **Recharts увеличивает размер frontend и добавляет внешнюю зависимость** → библиотека используется только через небольшой изолированный компонент, а версия фиксируется lock-файлом.

## План миграции и отката

1. Собрать образы и запустить PostgreSQL.
2. Выполнить миграции отдельным Compose-сервисом.
3. Запустить backend и дождаться успешного readiness.
4. Запустить Nginx с frontend.
5. При неудаче вернуть предыдущие теги образов; миграцию откатывать отдельно только после проверки совместимости и резервной копии.

Для первоначального развёртывания пользовательские данные отсутствуют, поэтому отдельный перенос данных не требуется.
